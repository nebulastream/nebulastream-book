13  Plugin Registries and Extensibility

NoteStatus: complete first draft

The vision statement in Chapter 1 listed extensibility as one of NebulaStream’s three pillars. This chapter is about how that pillar is built — specifically, how a plugin (a new source, sink, formatter, operator, or rewrite rule) gets compiled into the engine and made discoverable at runtime, all while staying compatible with C++’s static linking model.

The mechanism is a static plugin registry, generated by CMake at build time. It is one of the more interesting pieces of build-system engineering in NebulaStream and well worth understanding before you add your first plugin.

13.1 13.1 The problem static plugins solve

Plugins exist to keep the engine modular. A core team can ship the engine; third parties can ship sources, sinks, and rewrite rules without touching the core code. The engine discovers plugins at runtime via a registry; user code in the engine looks up “TCP” in the source registry and gets back a factory function for constructing TCP sources.

The implementation challenge is that C++ is a static-linking language. Unlike Java or Python, where adding a class to the classpath at runtime is a normal thing, C++ wants every symbol resolved at link time. There are dynamic loading mechanisms (dlopen, LoadLibrary) but they are awkward for production deployments and disastrous for embedded targets.

NebulaStream’s solution: every plugin is statically linked, and self-registers into a global registry at startup. This is the classic “register a class with itself” pattern. The trick is doing it without falling into the Static Initialisation Order Fiasco (SIOF) — the well-known C++ pitfall where the order of static initialisations across translation units is undefined.

The full solution is documented in docs/design/20240701_static_plugin_registry.md. The mechanism has five stated goals (G1–G5):

  • G1: Plugins must be statically linkable and self-register.
  • G2: Internal vs. external plugins must be cleanly separated.
  • G3: The mechanism must work for many extension types (sources, sinks, operators, types, functions, rewrite rules).
  • G4: Registration must be guaranteed (no “I forgot to declare this static instance” failures).
  • G5: Must not depend on initialisation order.

The fix for G5 is what makes the design interesting.

13.2 13.2 The CMake macros

A plugin author writes their plugin and one CMake macro invocation. The macros live in /Users/zeuchste/git/nebulastream/cmake/PluginRegistrationUtil.cmake. The two main entry points:

# nes-plugins/CMakeLists.txt
activate_optional_plugin("Sources/TCPSource" ON)
activate_optional_plugin("Sources/GeneratorSource" ON)
activate_optional_plugin("Sinks/VoidSink" ON)
activate_optional_plugin("InputFormatters/JSONInputFormatter" ON)
activate_optional_plugin("OutputFormatters/JSONOutputFormatter" ON)
if (NES_ENABLES_TESTS)
    activate_optional_plugin("Sinks/ChecksumSink" ON)
endif()

activate_optional_plugin turns on an optional plugin in the build. There is a corresponding add_plugin for built-in plugins that ship in the engine without an opt-in toggle.

What the macros actually do, behind the scenes, is generate a Registrar class — a single C++ file that contains, for each active plugin, the registration call. The generation is in generate_plugin_registrar:

# cmake/PluginRegistrationUtil.cmake (excerpt)
function(generate_plugin_registrar current_dir current_binary_dir
                                   plugin_registry plugin_registry_component)
    set(registrar_header_template_path
        ${current_dir}/registry/templates/${plugin_registry}GeneratedRegistrar.inc.in)
    file(READ ${registrar_header_template_path} registrar_header_file_data)

    foreach (reg_func IN LISTS plugin_registry_plugin_names_final)
        list(APPEND REGISTER_FUNCTION_DECLARATIONS
             "${plugin_registry}RegistryReturnType Register${reg_func}${plugin_registry}(${plugin_registry}RegistryArguments)")
        list(APPEND REGISTER_ALL_FUNCTION_CALLS
             "registry.addEntry(\"${reg_func}\", Register${reg_func}${plugin_registry})")
    endforeach ()

    configure_file(${temp_registrar_header_template_file}
                   ${registrar_header_generated_path} @ONLY)
endfunction()

The template file (<Type>GeneratedRegistrar.inc.in) declares forward declarations for every plugin’s Register* function and a single registerAll method that calls each. The plugin author provides the Register* function in their plugin code; CMake generates the file that calls them all.

13.3 13.3 The eager-init escape from SIOF

The Static Initialisation Order Fiasco arises when one global constructor uses another that has not yet been constructed. Self-registration through static MyPlugin instance{} traditionally suffers from this: which plugin’s constructor runs first? Which finds the registry already initialised?

NebulaStream sidesteps this with explicit initialisation:

  • The registry is not a global. It is created on-demand when first accessed (Meyers’ singleton pattern), so its lifetime begins at first use.
  • Plugin registration is not a static constructor. It is a function call inside registerAll, which is invoked explicitly from main() (or an equivalent fixed initialisation point in the worker startup).

The result is that registration order is well-defined: it is the order of registerAll’s sequential calls. The compiler is not asked to make any guarantee about cross-translation-unit ordering.

This is, in retrospect, the obvious solution. Most “self-registering plugin” patterns in C++ get this wrong; NebulaStream’s design is one of the cleaner implementations I have seen.

13.4 13.4 The plugin types

NebulaStream’s plugin system is generic. The currently-supported extension types:

Type Registry Examples
Source SourceRegistry TCP, File, Generator, Network
Sink SinkRegistry File, Print, Void, Checksum, Network
InputFormatter InputFormatIndexerRegistry CSV, JSON, Native
OutputFormatter OutputFormatterRegistry CSV, JSON, Native
LoweringRule LoweringRuleRegistry HashJoin, NLJoin
LogicalFunction LogicalFunctionRegistry arithmetic, comparison, UDFs

The “Network” sources and sinks moved from the optional-plugin tier to the built-in tier alongside the distribution layer (Chapter 19) — they are how operators on different workers communicate.

Each registry has the same shape: a string-keyed map from a type name to a factory function. The factory takes a descriptor (which encodes type-specific configuration) and returns an instance.

An earlier draft of this chapter listed a future-direction FunctionRegistry. That registry has since landed: see nes-logical-operators/registry/include/LogicalFunctionRegistry.hpp, which lets new logical functions be plugin-registered alongside sources, sinks, and formatters. The RewriteRuleRegistry for optimiser rules remains a future direction. The same CMake template machinery supports both without further engineering; the framework was designed for it.

13.5 13.5 Adding a new source: a worked example

Adding a new source plugin is the canonical “hello world” of NebulaStream extensibility. The full walkthrough is in docs/guide/extensibility.md and docs/guide/how_to_add_a_source.md. The shape:

  1. Create a new directory under nes-plugins/Sources/MySource/ (alongside the existing nes-plugins/Sources/TCPSource/) with a CMakeLists.txt and the plugin’s source files.
  2. The CMakeLists.txt calls add_plugin_as_library with the plugin name and the registry it belongs to.
  3. The plugin’s source provides a Register* function that the generated Registrar will call. The function body adds the factory function to the registry.
  4. Activate the plugin in nes-plugins/CMakeLists.txt with activate_optional_plugin("Sources/MySource" ON).
  5. Rebuild. The CMake regeneration picks up the new entry, the Registrar is regenerated, the worker’s startup code calls the plugin’s Register*, and “MySource” is now a valid TYPE in CREATE PHYSICAL SOURCE statements.

That is the entire user-facing surface: write a class, write a register function, add a CMake line, rebuild. No symbol-table contortions, no dynamic loading, no dlopen.

TipReal-system reference: how Telegraf and PostgreSQL handle this

Telegraf’s plugin system is a register-by-function-pointer pattern in Go, which has language-level support for init() functions that the runtime calls at startup. The mechanism is much simpler than NebulaStream’s CMake template machinery — but of course it requires a runtime. C++ does not have one.

PostgreSQL’s plugin system is dynamic: shared libraries (postgresql-contrib packages) are loaded with LOAD 'mymodule' at runtime, with each module’s _PG_init() doing registration. This is more flexible (you can add modules without rebuilding the server) but more dangerous (ABI compatibility is the user’s problem) and not viable for embedded deployments.

NebulaStream’s static-linked, CMake-generated registrar is the right answer for an engine targeting edge deployments where runtime dynamic loading is awkward and a rebuild is the expected mode of customisation.

13.6 Summary

NebulaStream’s plugin system is a static plugin registry generated at CMake-time. The framework supports sources, sinks, input/output formatters, and lowering rules through a single uniform mechanism: a string-keyed factory registry, populated by an explicitly-called registerAll function whose body is generated by CMake from a template. The design avoids the Static Initialisation Order Fiasco by replacing constructor-time self-registration with explicit initialisation. Adding a new plugin is a directory, a CMake line, and a Register* function — no dynamic loading, no manual registry edits.

13.7 Reading exercises

ImportantReading exercise 13.1: examine the generated registrar

After a build, find the generated Registrar files in your build directory:

find cmake-build-debug -name '*GeneratedRegistrar*'

Open one — say, the SourceGeneratedRegistrar — and read it. Confirm that every active source plugin appears, and that the function called from registerAll matches the plugin’s hand-written Register* function.

ImportantReading exercise 13.2: deactivate a plugin

In nes-plugins/CMakeLists.txt, change one activate_optional_plugin(... ON) to OFF for, say, the JSON formatter. Rebuild. What happens when you try to use the JSON formatter? You should get a binding error that the formatter type is unknown — caught by the registry lookup at query submission, not at runtime.

ImportantReading exercise 13.3: a tiny new sink

Sketch a BlackHoleSink that discards every record. The sink class is about 20 lines (execute does nothing). The registration is one CMake line and one Register* function. You do not need to actually build it; the exercise is to see how minimal the boilerplate is.
